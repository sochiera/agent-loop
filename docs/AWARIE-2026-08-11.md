# Dwie nocne awarie Forge — 2026-08-11

Zakres: dwie równoległe instancje Forge uruchomione wieczorem 10.08, obie
zatrzymane w nocy. Instancja A pracowała nad `project=paint-by-number`,
instancja B (zmodyfikowana do pracy równoległej) uruchamiała `forge.orchestrate`
z tego repozytorium. Źródła: wyjścia obu procesów, `git log`, stan plików
w `~/.claude` i `~/.config/forge/claude` odczytany 11.08 rano.

---

## 1. Werdykt w trzech zdaniach

Awarie mają **dwie różne przyczyny** i **jedną wspólną naturę**: obie instancje
dzieliły zasób, który nie znosi współdzielenia — najpierw katalog z kodem, potem
plik sesji OAuth. Instancja B padła na sprzeczności między kodem trzymanym
w pamięci procesu a szablonem promptu wczytywanym z dysku po commicie
`b11ccf1`; instancja A padła na wyścigu o rotujący refresh token Claude Code,
który przy okazji unieważnił także interaktywną sesję operatora.

Żadna z awarii nie była błędem logiki Forge — obie były błędami **operacyjnej
izolacji przebiegu**.

## 2. Awaria A — `OAuth session expired and could not be refreshed`

```
[01:03:45]   agent[plan] start: claude (próba 1)
[01:03:48]   agent[plan] BŁĄD: rc=1, 3s
"result":"Failed to authenticate: OAuth session expired and could not be refreshed"
```

Forge zatrzymał się poprawnie i zapisał checkpoint w
`/home/jan/Sources/paint-by-number/.forge/STATE.json` — zachowanie stopu jest
w porządku, problemem jest to, że w ogóle doszło do utraty sesji.

### Mechanizm

`_isolated_agent_env` w [`forge/agents.py`](../forge/agents.py) podpina sesję
CLI operatora do izolowanego domu Forge **dowiązaniem symbolicznym**:

```
~/.config/forge/claude/.credentials.json  ->  ~/.claude/.credentials.json
```

Założenie brzmi: jest jeden plik, więc odświeżenie widziane przez wszystkich.
Oba człony tego założenia są fałszywe.

1. **Dowiązanie nie przeżywa zapisu.** CLI zapisuje poświadczenia atomowo
   (zapis do pliku tymczasowego + `rename`), a `rename` podmienia dowiązanie na
   zwykły plik. Od pierwszego odświeżenia w izolowanym domu Forge ma **własną
   kopię sesji**, która nie widzi już nic, co robi CLI operatora.
2. **Refresh token jest jednorazowy.** Rotuje przy każdym użyciu. Gdy trzy
   strony (instancja A, instancja B, rozszerzenie VS Code) trzymają ten sam
   token, pierwsze odświeżenie unieważnia kopie pozostałych, a próba użycia
   zużytego już tokenu kasuje całą sesję po stronie serwera.

### Dowody ze stanu plików (odczyt 11.08)

| plik | stan | mtime |
|---|---|---|
| `~/.claude/.credentials.json` | zwykły plik, sesja żywa (`expiresAt` = 11.08 14:44) | **06:44:54** — ponowne logowanie operatora rano |
| `~/.config/forge/claude/.credentials.json` | **zwykły plik, nie dowiązanie**; `claudeAiOauth.accessToken` = `""`, `refreshToken` = `""`, `expiresAt` = `0`, `scopes` = `[]` | **01:03:46.125** — sekunda awarii |

Wyzerowana sekcja `claudeAiOauth` to zapis, który CLI zostawia po **nieudanym**
odświeżeniu. Plik przy okazji niesie tokeny OAuth serwerów MCP (`mcpOAuth`),
więc nie jest to plik do bezrefleksyjnego kasowania.

### Oś czasu

## 3. Awaria B — `ValueError: brak wartości promptu po-review.md: DROPPED, REOPENED`

```
[01:26:57]   agent[product-owner] start: codex (próba 1)
[01:29:02]   agent[product-owner] koniec: rc=0, 126s, wyjście 124378 znaków
ValueError: brak wartości promptu po-review.md: DROPPED, REOPENED
```

Tura PO **zakończyła się sukcesem** (126 s pracy modelu, 124 kB wyjścia).
Proces wywrócił się dopiero przy budowaniu promptu dla recenzentki — czyli
zapłacona praca poszła do kosza.

### Mechanizm

Commit `b11ccf1` powstał **10.08 o 22:36:29**, czyli **9 minut po starcie
instancji B** (~22:27). Dodał do
[`forge/prompts/templates/po-review.md`](../forge/prompts/templates/po-review.md)
sloty `{{DROPPED}}` i `{{REOPENED}}` oraz odpowiadające im argumenty
w `po_review_prompt` ([`forge/prompts/__init__.py`](../forge/prompts/__init__.py)).

Te dwie rzeczy ładują się w różnych momentach:

| element | kiedy trafia do procesu |
|---|---|
| kod `.py` | raz, przy starcie procesu → **stara** wersja `po_review_prompt` |
| szablon `.md` | przy KAŻDYM wywołaniu `render` → **nowa** wersja szablonu |

Stary kod nie przekazał dwóch nowych slotów, więc `render`
([`forge/prompts/render.py:27`](../forge/prompts/render.py#L27)) zgłosił brak.
**Zachowanie `render` jest poprawne** — fail-fast jest tu tańszy niż wysłanie do
modelu promptu z niepodstawionymi `{{...}}`. Wadliwy był stan operacyjny, nie
walidacja.

Awaria nie trafiła wcześniej, bo `po_review_prompt` wywołuje się dopiero po
pierwszej udanej turze PO — czyli po ~3 godzinach pracy.

### Dowód niezależny od dat

W tracebacku numery linii nie zgadzają się z treścią: ramka
`phase_product_owner` w linii 643 pokazuje komentarz o serii naruszeń, ramka
1807 — `git rev-parse --verify HEAD`, ramka `po_review_prompt` w linii 92 —
docstring `_story_reasons_block`. Python bierze numery linii ze skompilowanego
kodu w pamięci, a treść dociąga z dysku dopiero przy drukowaniu tracebacku.
Taki rozjazd występuje **wyłącznie** wtedy, gdy pliki źródłowe zmieniły się po
starcie procesu.

## 4. Znaleziska poboczne

1. **Izolowany dom Forge cicho rozjeżdża się z sesją operatora.** Ochrona
   z `_prepare_isolated_home` odtwarza dowiązanie przy każdym starcie procesu,
   ale w obrębie długiego przebiegu wystarczy jedno odświeżenie, żeby izolowany
   dom zaczął żyć własnym życiem. Awaria A to końcowy stan tego dryfu.
2. **Preflight nie sprawdzał sesji OAuth.** `ensure_provider_credentials`
   pilnowała kluczy API providerów OpenCode (bo `401` w środku roli kosztuje
   turę), ale dokładnie ten sam argument dotyczył Claude Code — i nie był
   zastosowany.
3. **Nie ma strażnika tożsamości kodu przebiegu.** Forge nie zapisuje, z jakiego
   commita ruszył, ani nie zauważa, że drzewo pod nim się zmieniło.

## 5. Wdrożone poprawki

### 5.1. Nierotujący token zamiast współdzielonego pliku sesji

Pliki: [`forge/agents.py`](../forge/agents.py),
testy w [`tests/test_agents.py`](../tests/test_agents.py).

- `claude_oauth_token()` czyta `FORGE_CLAUDE_OAUTH_TOKEN`, a w drugiej
  kolejności `CLAUDE_CODE_OAUTH_TOKEN`. Nazwa `FORGE_*` pozwala dać Forge inny
  token niż ten, którego operator używa we własnej powłoce.
- Gdy token jest ustawiony, `_isolated_agent_env` **nie podpina**
  `~/.claude/.credentials.json`. Znika współdzielony plik, znika wyścig
  o rotujący refresh token, znika kolizja z rozszerzeniem VS Code.
- `_disable_shared_credentials` odsuwa pozostałość po trybie plikowym do
  `.credentials.json.disabled` — przenosi, a nie kasuje, bo plik bywa jedynym
  nośnikiem tokenów OAuth serwerów MCP.
- Tryb plikowy działa dalej bez zmian: brak tokenu = dotychczasowe zachowanie.

Token z `claude setup-token` nie rotuje, więc dowolnie wiele instancji może go
używać równolegle. Włączenie:

```bash
claude setup-token                       # wypisuje token
export CLAUDE_CODE_OAUTH_TOKEN=...       # albo FORGE_CLAUDE_OAUTH_TOKEN=...
```

Token można też wpisać do pliku `*.env` obok konfiguracji OpenCode (albo
wskazanego przez `FORGE_ENV_FILES`) — preflight dobierze go tak samo, jak klucze
providerów. To ta sama luka, którą opisuje
[`forge/provider_env.py`](../forge/provider_env.py): proces z crona albo
z launchera desktopowego nie dziedziczy środowiska powłoki.

**Alternatywa minimalna, jeśli ktoś nie chce tokenu:** nie uruchamiać dwóch
instancji `claude` równolegle na jednym koncie i nie używać w tym czasie
rozszerzenia VS Code.

### 5.2. Preflight sesji Claude Code

Pliki: [`forge/preflight.py`](../forge/preflight.py),
[`forge/config.py`](../forge/config.py),
testy w [`tests/test_preflight.py`](../tests/test_preflight.py).

`ensure_claude_session` czyta jeden JSON przed startem pętli i zatrzymuje
przebieg zanim ktokolwiek zapłaci za turę agenta. Rozpoznawane stany:

| stan | reakcja |
|---|---|
| ustawiony token OAuth | pomijamy plik całkowicie |
| brak/nieczytelny plik sesji | zgłoszenie |
| `accessToken`/`refreshToken` puste albo `expiresAt = 0` | zgłoszenie (dokładny stan z 01:03:46) |
| `refreshTokenExpiresAt` w przeszłości | zgłoszenie |
| sam `accessToken` wygasły, refresh token żywy | **cisza** — CLI odnowi go sam |

Ostatni wiersz jest istotny: wygasły access token to stan normalny, a
zatrzymywanie na nim przebiegu byłoby fałszywym alarmem droższym niż awaria,
przed którą chroni.

Polityka zatrzymania jest ta sama, co przy kluczach providerów
(`roles_blocked_by`): niesprawna sesja przerywa start tylko wtedy, gdy jakaś
rola nie ma już czym pracować. Służy do tego nowe
`Config.roles_requiring_agent(agent)` — zwraca etykiety `rola/trudność`, których
cały łańcuch (wybór + zapasy) prowadzi do jednego narzędzia. Przy domyślnym
routingu jest to 18 kombinacji dla `claude`, więc martwa sesja OAuth naprawdę
zatrzymuje start; rola z działającym zapasem dostaje tylko wpis do dziennika.

Wynik trafia do `PreflightResult.claude_session`.

Testy: 506 przechodzi (`python3 -m pytest -q`, 8,4 s).

## 6. Propozycje niewdrożone

### 6.1. Snapshot kodu na przebieg (naprawa awarii B)

Jedyne pełne rozwiązanie: każda instancja startuje z własnego `git worktree`
albo kopii `forge/`, a repozytorium robocze nigdy nie jest tym samym drzewem, do
którego operator commituje. Nie zaimplementowane, bo dotyka sposobu
uruchamiania, a nie kodu Forge — to decyzja operacyjna.

Uwaga: cache'owanie szablonów w pamięci procesu (`lru_cache` na
`read_template`) **nie jest** rozwiązaniem — przesuwa tylko moment rozjazdu na
pierwsze użycie danego szablonu.

### 6.2. Strażnik tożsamości kodu

Wariant tani: zapisać `git rev-parse HEAD` katalogu Forge przy starcie i na
granicy iteracji przerwać z czytelnym komunikatem, gdy HEAD się zmienił.
Świadomy restart zamiast losowego `ValueError` po trzech godzinach pracy.
Warto, jeśli commitowanie pod działającą pętlą ma pozostać normalną praktyką.
